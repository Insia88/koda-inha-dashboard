# 운영 도입 전 남은 조건

이 앱은 개발 환경에서 기능·권한·데이터 일관성을 검증하기 위한 것이다. 아래가 충족되기 전에는 실제 고객·자산에 사용할 수 없다. UI·테스트 통과가 인증·보안·규제 적합성을 증명하지 않는다. 공개 데모(Vercel)의 구성·설정·검증·되돌리기는 [deploy-vercel.md](deploy-vercel.md)에 있다. 공개 데모도 아래 조건을 하나도 충족하지 않은 개발용 앱이다.

## 반드시 교체·구현할 부분
| 영역 | 현재 | 운영 조건 |
| --- | --- | --- |
| 인증 | `AUTH_MODE=dev` 비밀번호 없는 모의 로그인. `VERCEL=1` 또는 `NODE_ENV=production`이면 서버가 기동을 거부하고, `DEMO_PUBLIC=1`을 명시했을 때만 공개 데모(같은 모의 로그인·모의 데이터)로 뜬다. 로컬은 127.0.0.1 등 자기 컴퓨터 주소로만 연다(`DEV_ALLOW_LAN=1`로만 해제) | KODA SSO/OIDC 어댑터 구현(`server/auth.ts`의 세션 생성부 교체), MFA·세션 만료 정책·재인증(승인 직전) 결정, `/api/auth/dev-users` 제거, 공개 데모 예외(`DEMO_PUBLIC`) 경로 제거 |
| 커스터디 | `MockCustodyAdapter` — 일정 시간 뒤 '처리 완료'로 표시만 함. **멱등 키 계약:** 승인 트랜잭션 안에서 상태를 처리 중으로 바꾸기 바로 앞에 `submitWithdrawal({requestId, idempotencyKey, …})`를 호출하고 키는 요청 id다. 어댑터는 같은 키로 다시 오면 새 출금을 만들지 않고 처음 접수 참조를 돌려줘야 한다(키가 비면 거부). 모의 어댑터는 프로세스 메모리에서 키를 기억한다 | 실제 커스터디 API 어댑터(`server/adapters/custody.ts` 인터페이스), 서명·콜드룸 절차와 상태 매핑, 실패·부분 처리·재시도 규칙. **아웃박스 필수:** 지금은 외부 호출이 DB 트랜잭션 안에 있어, 호출은 성공했는데 커밋이 실패하면 KODA 쪽에만 접수가 남을 수 있다. 운영에서는 승인 커밋과 함께 '보낼 접수'를 아웃박스 테이블에 쓰고 별도 작업자가 같은 멱등 키로 전송·재시도·결과 반영하며, KODA 쪽도 같은 키를 중복 접수로 처리해야 한다. '처리 완료'의 기준(KODA 서명·블록체인 확정)과 거래 해시 표시도 정한다(A-26) |
| 주소 검증 | `MOCK-` 형식만 허용. 유사 주소(lookalike-v2)·가운데 8자리 재입력은 설계 가정(A-05, A-07) | 네트워크별 실제 주소 형식·체크섬 검증 어댑터, 지원 자산·네트워크 목록을 KODA 기준으로 동기화. 유사 주소 기준·재입력 길이·신규 주소 사용 대기 시간·확인 인원은 KODA와 결정(DEC-003) |
| 시세 | 고정 모의 값. 기준 시각이 30분 넘게 오래되었거나 읽을 수 없거나 5분 넘게 미래이면 승인 수를 고액 기준으로 올린다(fail closed, A-03) | 시세 제공처 계약·출처 표기·지연 기준 결정. 시세 장애 때 승인 인원이 늘어나는 것을 업무 절차로 받아들일지 결정 |
| 저장소 | 단일 파일 SQLite. 공개 데모는 인스턴스 메모리(재시작 때 초기화, A-23) | 다중 인스턴스면 PostgreSQL 등으로 이전(동일 제약: 부분 고유 인덱스, 감사 불변 트리거·권한 분리, `SELECT … FOR UPDATE` 또는 버전 검사), 백업·암호화·보존 기간 |
| 감사 기록 | 조직별 해시 체인(새 기록은 v2, 수행자 이름 포함) + UPDATE/DELETE 금지 트리거. 검증은 중간 수정·삭제를 찾지만 가장 최근 기록 삭제는 찾지 못한다. 기존 v1 기록은 수행자 이름을 보호하지 못한다(`npm run db:reset`으로 만든 DB는 모두 v2) | DB 계정 권한 분리(앱 계정 INSERT만), 외부 WORM 저장소 또는 주기적 해시 앵커링. **앵커링 절차:** 감사 담당자가 검증 결과의 `headHash`·`count`를 정기적으로 앱 밖(별도 저장소·문서)에 남기고 다음 검증과 대조해야 최근 기록 삭제가 드러난다. 보존·열람 정책 |
| 요청 한도 | 프로세스 메모리 기반. 공개 데모는 인스턴스마다 따로 센다 | 여러 인스턴스면 공유 저장소(Redis 등) |
| 비밀값 | 없음(개발 모드는 비밀값 불필요). 공개 데모는 쿠키 Secure | 쿠키 `secure` 활성(HTTPS), 비밀값 관리 시스템 |

## 알아 둘 동작 (개발·데모 운영)
- `MOCK_PRICE_FEED=off`로 실행하면 30분 뒤 시세가 지연 상태가 되어 모든 제출이 고액 기준(2명)으로 바뀐다. 승인자가 1명뿐인 모의법인 B는 이때 모든 제출이 422 `APPROVERS_INSUFFICIENT`로 거부된다(의도한 동작, A-16).
- 받는 주소를 사용 중지하면 그 주소로 가는 승인 대기 요청은 자동으로 반려되지 않는다. 승인자가 반려하거나 요청자가 취소해야 예약 수량이 풀린다(A-17).
- 공개 데모의 데이터·세션·요청 한도는 인스턴스마다 따로 있고 재시작 때 초기화된다. 인스턴스당 새로 만들 수 있는 주소·요청·인사이트는 종류별 200건이다(`DEMO_LIMIT`). 자세한 한계는 [deploy-vercel.md](deploy-vercel.md) 4절.

## KODA 측 확인이 필요한 자료
- 실제 역할·권한 매핑, 요청 상태 체계와 전이, 승인 인원·한도 정책 (`assumptions.md` A-01~A-05, A-15~A-21)
- 지갑별 결재선(생성 단계·n차 승인) 사용 여부와 최고관리자·지갑 관리자 우회의 업무상 필요 (A-20, A-21, DEC-002)
- 주소록 등록 절차·확인 주체·확인 인원, 신규 주소 사용 대기 시간, 지원 네트워크별 메모/태그 규칙 (DEC-003)
- 트래블룰 수취인 정보·VASP 목록·확약서 제출과 상태, 일치 규칙 (A-14, OPEN-002)
- '처리 완료'의 기준과 KODA 처리 단계(보류 포함) (A-26)
- Market Insight 기관 화이트리스트 운영 기준, 원문 표시·이용 권한
- 익명화된 법인 고객 인터뷰(사용자 과업 우선순위) — 현재 미수령

## 보안 점검 항목(구현됨, 운영에서 재검증 필요)
서버 측 역할·조직 검사(모든 API), 타 조직 리소스 404, CSRF 헤더 + SameSite=Strict, HttpOnly 세션·서버 폐기, 입력 Zod 검증·본문 64KB 제한, 오류 응답에 스택·내부 값 없음, 로그에서 쿠키·CSRF 가림, CSP·보안 헤더(공개 데모는 CDN 응답에도 같은 정책), CSV 수식 무력화, 내보내기 권한·기록, 자기 승인·자기 주소 확인·자기 역할 상승 금지, 사용 중지 주소로의 승인 거부, 감사 기록에 전체 주소 대신 끝 6자리만 기록.
