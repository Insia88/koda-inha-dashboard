# KODA 법인 대시보드 사용성 시험 키트

8명 대면 과업 시험과 온라인 트리 테스트를 이 문서 하나로 준비하고 진행할 수 있게 묶었다. `app/docs/structure-benchmark.md` 6절(검증 계획)을 바탕으로 했고, 같은 문서 5.5절(KODA가 결정할 항목), `app/docs/traceability.md`의 'A1 화면 문구·배치' 절, `app/docs/assumptions.md`, `docs/dashboard.md`의 검증 과업 T-001~T-006, `app/DESIGN.md`를 함께 참고했다.

- 화면 속 회사·사람·주소·금액은 모두 저장소 시드(`app/server/seed.ts`)의 모의 데이터다. 이 키트에서 새로 만든 소품(모의 거래처 M 인보이스, 거래처 대장, 정산서, 품의서, 정산 명세서, 전화번호)도 모두 가상이다.
- KODA 이용가이드(S3)는 쓰지 않았다. 문구도, 화면도, 예시도 가져오지 않았다.
- 숫자 기준(1억 원, 24시간, 끝 6자리, 가운데 8자리 등)은 저장소의 설계 가정이다. KODA의 정책이 아니다.
- **기준 빌드**는 `feat/enterprise-dashboard`에서 A2·A2b가 든 커밋이다. A1은 `f1f9088`에, A2와 A2b는 2026-10-21 `5e44293`에 합쳐졌다(그 뒤 `37d0b8f`는 문서만 더했다). 정확한 해시는 11절 '기준 커밋 확정' 때 정해 적고, 시험 주간에는 빌드를 바꾸지 않는다(12절). 이 빌드에는 A2b가 들어 있으므로, 세션 전에 WR-000003·WR-000004에 정산 명세서·품의서 PDF를 지급 근거로 넣은 시험용 시드를 만든다. 근거는 승인 요청 뒤에는 붙일 수 없기 때문이다(4.1절). 만들지 못하면 1.3절 나의 A2b 행은 판단 보류로 둔다.

## 1. 목표와 결과가 정할 일

### 1.1 목표

1. **첫 실제 사용자 자료를 얻는다.** 디지털 자산 업무 경험이 없는 법인 재무·관리 담당자가 화면만 보고 핵심 업무를 끝낼 수 있는지, 어디서 막히는지 본다. 지금까지 있는 근거는 AI 에이전트가 가상 인물을 연기한 워크스루뿐이다(benchmark 1절).
2. **보호 장치가 실제로 쓰이는지 본다.** 확인할 것은 네 가지다.
   - 가운데 8자리를 원본에서 읽는지, 화면 글자를 옮겨 치는지
   - 등록자와 상관없는 연락처로 다시 확인하는지
   - 근거 문서를 보고 나서 수량 체크를 하는지
   - 휴대폰에서 주소를 대조한 뒤 체크하는지
3. **A1과 A2를 판단한다.** A1 변경(A1-01~A1-12)을 유지할지 보완할지 정한다. A2 항목을 유지할지도 확인한다(기준 빌드에 A2가 들어 있다). A2 항목은 승인할 수 있는 사람 이름, 승인 화면의 주소 기록, 결정 근거 첨부와 메모, 감사 CSV 표지다.
4. **B안이 필요한지 가린다.** 메뉴를 업무 단위로 다시 짜는 B안이 필요한지는 트리 테스트 결과와 과업 시험의 실패 원인으로 판단한다.
5. **KODA 결정 항목에 넣을 근거를 모은다.** 대상은 benchmark 5.5절의 1·2·3·5·6·7·9·10·11·12번이다. 결정은 KODA가 한다.

### 1.2 하지 않는 것

- **보호 효과를 숫자로 주장하지 않는다**(DASH T-006, benchmark 6.2절). 심어 둔 이상이 실제 업무보다 훨씬 자주 나오므로, 발견율은 상한으로만 읽는다.
- **접근성 점검은 따로 한다.** 키보드만으로 쓰기, 스크린리더, 200% 확대는 전문가가 별도로 점검한다(benchmark 6.1절).
- **범위 밖 항목:** Market Insight(T-005), 실서비스 상태·권한 체계 대조, 신규 직원 초대(A-10, 기능 없음).
- **A1 이전 화면(`2a887b7`)과 같은 사람에게 번갈아 써 보게 하는 비교는 기본 계획에 넣지 않았다.** 승인자 3명으로는 정성 비교만 가능한데, 세션 시간이 30분 늘기 때문이다. 필요하면 승인자 결정 카드 하나만 골라 benchmark 6.1절의 교차 방식으로 추가한다. 그래서 이 시험만으로는 'A1이 이전보다 낫다'는 결론을 내리지 않는다. 판단할 수 있는 것은 'A1이 겨냥한 문제가 실제 사람에게서 다시 나오는가'다.

**1번 판정 규칙.** T2(요청자 3)와 T4 (가)(승인자 3)를 한 6명의 `mid8_source`를 센다. | 결과 | 읽는 법 |
| --- | --- |
| screen·mixed가 4명 이상 | 순서를 바꾸자는 근거(benchmark 6.3절 살리는 조건, 결정 요청 7번) |
| screen·mixed가 1명 이하이고 original이 4명 이상 | 지금 순서를 유지할 근거(benchmark 6.3절 버리는 조건 '다수가 원본에서 글자를 읽음', 결정 요청 7번) |
| 그 밖(screen·mixed가 2~3명이거나, unclear·na가 많아 위 두 줄에 들지 않음) | 판단 보류. 결론을 내지 않고 이유를 적으며, KODA에는 값별 사람 수만 전한다 |

- 세 줄은 서로 겹치지 않으므로 한 결과에 결론이 하나만 나온다.
- 유지 쪽에 'screen·mixed 1명 이하'를 함께 건 것은 benchmark 6.3절에는 없는 조건이다. 6명 중 2명이 옮겨 친 결과를 '유지'로 넘기지 않으려는 것이며, 결정 요청 7번도 같은 조건을 쓴다. 기준을 바꾸려면 첫 세션 전에 이유와 날짜를 적고, 이 키트와 결정 요청 7번을 함께 고친다.
- screen·mixed 사례는 판정과 별개로 하나하나 `issues.csv`에 심각도 3으로 올린다(6절 T2 관찰 행, T4 부분 행).

**라. B안이 필요한지.** 아래 두 조건이 **모두** 맞을 때만 업무 중심 개편을 KODA에 제안한다.

1. **트리 테스트(구조당 30명 이상):** 참가자별 전체 성공률의 평균이 B안에서 15%p 이상 높고, 그 차이의 95% 신뢰구간 하한이 0보다 크다. 핵심 과업 1~4번 가운데 B안이 10%p 이상 낮은 과업도 없다.
2. **대면 과업 시험:** 실패·포기와 심각도 3 이상인 문제 가운데 원인이 '메뉴에서 갈 곳을 못 찾음'(`cause_type=navigation`)인 것이 절반 이상이다.

그 밖에는 이렇게 처리한다.

- **조건을 채우지 못하면** A안(A1과 A2)을 유지하고, 트리 오답이 몰린 이름만 고친다.
- **참가자 다수가 홈 할 일 카드로만 들어온다면** B안을 제안하지 않을 근거로 기록한다(benchmark 6.3절).
- **트리 테스트 인원이 구조당 30명에 못 미치면** B안 판정은 미룬다. 트리 결과는 메뉴 이름 혼동을 찾는 데만 쓴다.
- **15%p 기준**은 이 키트가 제안한 값이다. 첫 세션 전에 과제팀이 확정한다.

**관리·감사 두 사람은 모두 윤가람 카드로 3초 테스트를 한다.** 자극물과 채점 기준이 윤가람의 홈이기 때문이다(5.5절). P08은 3초 테스트가 끝나면 문태호 카드로 바꾸고, 노트북은 처음부터 문태호로 로그인해 둔다(4.6절). 로그인해 둔 화면은 3초 테스트가 끝날 때까지 가려 두므로, P08이 윤가람 카드를 든 동안 문태호의 화면을 보는 일은 없다. T7과 T8의 순서를 바꾸는 장치는 그대로다.

여기에 예비 2명(요청자 1, 승인자 1)과 파일럿 1명(결과 집계 제외)을 더 모집한다.

**공통 조건**

- 법인 재무·회계·자금·경영지원·내부감사 실무 2년 이상
- 기업뱅킹 결재나 전자결재를 써 본 경험
- 디지털 자산 업무 경험 없음

**역할별 조건**

- 승인자는 평소 결재권자로 일하는 팀장급 이상으로 뽑는다. 그중 2명 이상은 평소 화면 확대나 큰 글씨를 쓰는 사람이다(benchmark 6.1절).
- 관리·감사 참가자는 1명은 시스템·권한 관리, 1명은 내부감사·회계 쪽이 좋다.

**섞을 것:** 회사 규모(대기업·중견·중소)와 업종을 섞는다. 같은 회사 사람은 2명까지만 받는다.

**8명이면 무엇을 찾을 수 있나.** 8명은 문제를 찾기 위한 규모다. 참가자 3명 중 1명꼴로 겪는 문제가 한 번이라도 드러날 확률은 1−(2/3)^n으로 계산한다.

| 그 과업을 한 사람 수 | 드러날 확률 | 해당 과업 |
| --- | --- | --- |
| 2명 | 약 56% | 관리·감사 과업 |
| 3명 | 약 70% | 역할 과업 |
| 8명 | 약 96% | T1, 3초 테스트 |

그래서 관리·감사 과업에서 아무 문제도 보이지 않았다고 해서 문제가 없다고 쓰지 않는다.

- 이름과 연락처는 S12 뒤 마지막에 받는다.
- S1~S6의 제외 조건에 걸리면 설문을 그 자리에서 끝내고 "이번 시험의 조건에 맞지 않아 여기서 마칩니다. 시간 내 주셔서 고맙습니다."를 보인다. 이름과 연락처는 받지 않는다.

## 4. 준비

### 4.1 실행 환경: 세션마다 같은 처음 상태

- **공개 데모 주소(`koda-inha-dashboard.vercel.app`)는 쓰지 않는다.** 누구나 같은 데이터를 바꿀 수 있고(DEC-004), 다시 시작하면 초기화되어(A-23), 세션마다 같은 시작 상태를 보장할 수 없다.
- **시험용 노트북을 따로 둔다.** 기준 커밋을 받은 시험 전용 폴더에서 로컬로 띄운다. `D:` 드라이브는 공간이 거의 없으므로 시험용 노트북을 따로 두는 편이 낫다.
- **포트는 4520을 쓴다.** 4300·4400·4410은 쓰지 않는다.
- **새 주소 사용 대기는 기본값 24시간 그대로 둔다.** `ADDRESS_COOLDOWN_HOURS=0`을 주지 않는다.

```powershell
# 처음 한 번 (시험용 폴더의 app 안에서)
npm ci
npm run build

# 세션마다: 서버를 멈춘 뒤 DB를 다시 만들고 띄운다 (세션 시작 15분 안쪽)
$env:DB_PATH = './data/ut.sqlite'
$env:PORT = '4520'
npm run db:reset
# 휴대폰 접속이 필요할 때만 아래 두 줄. 리허설에서 접속이 되는지 먼저 확인한다
$env:HOST = '0.0.0.0'
$env:DEV_ALLOW_LAN = '1'
npm start
```

- **초기화 시점이 중요하다.** 시드의 시각은 초기화한 때를 기준으로 계산된다('4시간 전', '20일 전' 등). 그래서 초기화는 세션 직전에 한다. 사용 대기 주소 L은 초기화 뒤 22시간이 지나야 사용할 수 있다.
- **휴대폰은 노트북 핫스팟에 시험용 기기만 연결한다.** 세션이 끝나면 `HOST`와 `DEV_ALLOW_LAN`을 끄고 서버를 다시 띄운다. 접속이 안 되면 노트북 Chrome 기기 모드(390×844)를 대신 쓰고, 그 사실을 `device` 열에 적는다.
- **기준 커밋 해시를 기록한다.** 세션마다 `participants.csv`의 `build_commit`에 적는다.

**지급 근거를 넣은 시험용 시드(A2b)**

- A2와 A2b는 2026-10-21 `feat/enterprise-dashboard`에 합쳐졌다(`5e44293`). 기준 빌드에 A2b가 들어 있으므로 아래 시험용 시드는 반드시 만든다(머리말).
- A2b는 출금 요청에 '지급 근거' 파일(PDF·PNG·JPEG)과 '지급 근거 메모'를 붙이는 기능이다(`docs/decisions.md` DEC-005, `app/docs/assumptions.md` A-38). 근거는 그 요청을 쓴 사람만, 요청이 작성 중이거나 검토 중일 때만 붙일 수 있다. 승인 요청을 보내면 근거가 고정되어 더 붙이거나 지울 수 없다. 근거가 없는 요청은 결정 카드에 '근거 기록 없음'으로 보인다.
- 시드에는 어느 요청에도 지급 근거가 없다. WR-000003(한지수 작성)과 WR-000004(강도윤 작성)는 처음부터 승인 대기다. 그대로 두면 두 건 모두 '근거 기록 없음'으로 보이고, 화면에서 근거를 붙일 수도 없다. 시드에서 근거를 붙일 수 있는 상태의 요청은 한지수의 WR-000005(검토 중, XRP)와 WR-000006(작성 중, KAIA)뿐인데, T5·T6 대상과 내용이 다르다.
- 그래서 시험용 폴더의 시드만 고쳐 시험용 시드를 만든다. WR-000003·WR-000004를 작성 중이나 검토 중 단계에 두고, 그 요청을 쓴 사람이 붙인 것으로 정산 명세서·품의서 PDF(4.4절, 책상 위 종이와 같은 내용)를 지급 근거로 넣은 다음 승인 대기로 넘긴다. 저장 계층이 승인 대기인 요청에 근거를 넣는 것과 작성자가 아닌 사람 이름으로 넣는 것을 막으므로, 이 순서를 지켜야 한다. 저장소의 시드는 고치지 않는다.
- 두 건 모두 넣는다. 한 건에만 넣으면 카드의 차이가 '이 건을 확인하라'는 신호가 된다(12절).
- 근거 파일은 DB 안에 저장된다. `db:reset`은 시드를 다시 넣으므로, 시험용 시드를 쓰면 세션마다 같은 근거가 다시 들어간다. 시험용 시드로 초기화한 세션은 `participants.csv`의 `notes`에 `test_seed`를 적는다.
- 파일럿에서 두 건의 결정 카드에 지급 근거가 보이는지, 파일을 내려받아 열 수 있는지 확인한다. 시험용 시드를 만들지 못하면 1.3절 나의 A2b 행은 판단 보류로 둔다.

### 4.3 인물 카드 (참가자에게 주는 것)

**인물 카드와 과업 카드에는 화면 낱말을 쓰지 않는다.**

- **8.2절의 금지 낱말은 인물 카드와 과업 카드에도 적용한다.** 대면 시험은 A1 화면만 보므로, 그 목록 가운데 현재(A1) 메뉴 낱말과 역할 이름(자산 담당자, 승인자, 감사 담당자, 조직 관리자)을 막는다. 8.2절처럼 어간 기준으로 본다. 예: '보낼 곳'이 막히면 보내야·보낸·보낼 수도 막는다. '우리 회사'가 막히면 '회사'도 막는다.
- B안에만 있는 낱말(처리, 거래처, 올린, 받기 등)은 대면 카드에 써도 된다. 참가자가 B안 화면을 보지 않기 때문이다.
- 대상을 가리키는 고유 이름(사람 이름, 모의 거래처·그룹사 이름, 요청 번호 WR-…)은 쓴다. 금지 낱말이 든 시드 데이터 이름(예: '신규 거래처 G 입금 주소')은 카드에 그대로 옮기지 않고 거래처 이름으로 가리킨다.
- 카드를 인쇄하기 전에 두 사람이 따로 대조하고, 결과를 기록한다.

**로그인은 진행자가 미리 해서 홈 화면에서 시작한다.** 로그인 화면에는 역할 설명이 나오기 때문이다. 로그인해 둔 화면은 3초 테스트가 끝날 때까지 가려 둔다(4.6절).

> **한지수 (모의법인 A 재무팀)** — 거래처가 대금을 받을 지갑을 대시보드에 미리 올려 두고, 송금할 건을 만들어 결정권자에게 올립니다. 송금을 결정하는 일은 하지 않습니다.
>
> 최근에 한 일:
> - 어제 신규 거래처 L의 지갑을 올렸고, 오늘 서예린 CFO가 대조를 마쳤습니다.
> - 어제 신규 거래처 G의 지갑을 올렸습니다.
> - 어제 정산 파트너 B 앞 4분기 정산 1차분 송금 건을 올렸습니다.
> - 오늘 XRP와 KAIA 송금 건 두 개를 만들다가 멈췄습니다.

> **오민재 (모의법인 A 재무팀장)** — 직원이 올린 송금 건을 보고 송금할지 결정하고, 새로 올라온 거래처 지갑이 맞는지 대조합니다. 본인이 송금 건을 만들지는 않습니다. 근거 서류는 보통 그 건을 올린 직원이 메일로 전해 줍니다(오늘은 책상 위 종이).

> **윤가람 (모의법인 A IT 보안팀)** — 대시보드에서 직원마다 무엇을 할 수 있는지 정하고 바꿉니다. 송금 일은 하지 않습니다.

> **문태호 (모의법인 A 내부통제팀)** — 대시보드에서 지난 송금과 결정의 흔적을 찾아보고, 외부 회계법인이나 사내 점검에 필요한 자료를 준비합니다. 다른 사람의 일을 바꾸지는 못하고 보기만 합니다.

### 5.4 진행 규칙: 중립 질문, 개입, 도움 기록

**쓰는 말**

- "지금 무엇을 보고 계세요?"
- "지금 무엇을 하려고 하세요?"
- "그 부분을 조금 더 말씀해 주시겠어요?"
- "말씀 이어 가 주세요."
- 참가자가 "이거 맞아요?"라고 물으면: "평소라면 어떻게 하시겠어요?" / "지금 화면만 보고 판단하신다면요?"
- 무엇을 눌렀는지 물을 때: "그걸 누르실 때 무엇을 기대하셨어요?"
- 고마움 표시는 "고맙습니다"만 한다.

**쓰지 않는 말**

- 화면 낱말로 이끄는 말: "결재 및 요청을 눌러 보세요", "가운데 8자리는 원본에서 보세요"
- 맞았다고 알려 주는 말: "잘하셨어요", "맞습니다"
- 신중함을 부추기는 말: "꼼꼼히", "정확히", "조심해서"
- 다른 참가자 이야기

**개입**

- **3분 동안 진전 없이 같은 곳을 맴돌거나 포기 의사를 밝히면** 이렇게 말하고 결과를 '포기'로 기록한다. "여기까지 하고 다음으로 넘어가도 괜찮습니다. 어떤 점이 걸리셨는지 말씀해 주시겠어요?"
- **제한 시간을 넘기면** '시간 초과'로 기록한다.
- **앱 오류나 서버 문제**는 진행자가 복구하고, 그 시간은 과업 시간에서 뺀다.
- **참가자가 실제 개인정보를 입력하려 하면** 바로 멈춘다.

**도움 기록 (`assists` 열)**

| --- | --- | --- |
| 계속하라는 말 | — | 도움으로 세지 않는다 |

### 5.6 과업 진행 공통 문장

> 과제 카드를 읽어 드리고 같은 카드를 드리겠습니다. 다 읽으시고 "시작"이라고 말씀하시면 시작합니다. 끝났다고 생각되시면 "끝났습니다"라고 말씀해 주세요. 어느 과제든 연락이 필요하면 번호를 말씀하시고 전화하는 것처럼 하시면 됩니다. 책상 위 자료도 어느 과제에서든 쓰셔도 됩니다.

- 이 문장은 **모든 과업 앞에서 똑같이** 읽는다. 전화 안내를 특정 과업 카드에만 넣으면, 그 문장이 '이 건은 확인할 것이 있다'는 신호가 되기 때문이다. 그래서 과업 카드에는 전화 안내를 넣지 않는다.
- 같은 이유로 T5·T6의 두 카드는 같은 틀의 문장으로 쓰고, 다른 것은 요청자·대상·근거 문서 이름뿐이다(6절 T5).

과업이 끝나면 SEQ 용지를 드린다(7절). 결정 과업(T4~T6)에는 확신 문항을 더하고, 과업마다 정해 둔 회고 질문을 한다(6절). 회고 질문은 과업이 끝난 뒤에만 한다. 다만 T5가 끝나면 SEQ와 확신만 묻고, T5·T6 두 건에 대한 질문은 T6가 끝난 뒤 함께 한다(6절 T5).

- **관찰:** 근거 문서를 실제로 보고 수량 체크를 했는지(`evidence_checked`). 결정 카드의 지급 근거를 알아봤는지, 대조에 카드 파일과 종이 가운데 무엇을 썼는지(`notes`). 결정 카드 맨 위 요약을 읽었는지. 전체 주소를 문서와 맞춰 봤는지(`address_compared`). 지문을 대조하려 했는지. 점검 목록과 저장된 진행 사유를 읽었는지. 버튼 이름('승인하고 처리 시작'과 '승인')에 대한 반응.
- **T5가 끝나면 SEQ와 확신(7.2절)만 묻는다.** 버튼 질문과 주소 기록 질문은 T6가 끝난 뒤로 미룬다. T5와 T6 사이에 승인 버튼이나 주소 기록을 물으면, 참가자가 T6에서 승인 효과 문장·버튼·주소를 일부러 읽고 더 조심하게 된다. 그러면 T6에서 보는 A1-05(대조 띠를 문서와 맞춰 봤는지)와 A1-06(T6 건의 `button_effect_known`)의 '유지'가 부푼다.
- **T6 뒤 질문(결정과 상관없이 두 건 모두, 같은 말로):** T6의 SEQ와 확신을 받은 뒤 한다. 승인·반려·보류 가운데 무엇을 했든 묻는다. 묻기 전에 두 화면을 모두 가린다(노트북 외부 모니터는 T6 동안 꺼 둔 그대로 두고, 휴대폰은 뒤집어 둔다). 결정한 순서대로 T5 건부터 묻는다. 건을 가리킬 때는 과업 카드에 쓴 이름만 쓴다(예: "강도윤 님이 올린 그룹사 C 앞 BTC 이전 건").
  1. 버튼 질문, 건마다 먼저 기억으로 묻는다: "[그 건]을 결정하실 때 화면에 승인 버튼이 있었습니다. 그 버튼은 누르면 어떤 일이 일어나는 버튼이었나요?"
  2. 버튼을 기억하지 못하거나 "모르겠다"고 하면, 미리 캡처한 그 건의 결정 카드 이미지를 보여 주고 버튼을 가리키며 같은 질문을 한다. 이미지는 그 건을 결정한 기기의 폭으로 쓴다(T5 건은 1440px, T6 건은 390px).
  3. 주소 기록 질문, 건마다: "[그 건]을 결정하실 때 받는 주소가 맞는지는 무엇을 보고 판단하셨나요?"
  - 기록: `button_effect_known`은 두 건 모두 적는다. T5 건의 답은 T5 행에, T6 건의 답은 T6 행에 적는다. 정답은 WR-000004가 '바로 수탁사 처리가 시작된다', WR-000003이 '한 명이 더 승인해야 처리가 시작된다'이다. `button_effect_source`에는 기억으로 답했으면 `memory`, 이미지를 보고 답했으면 `image`를 적는다. 주소 기록 질문의 답은 그 건 행의 `notes`에 적는다. 1.3절 나의 '승인 화면의 주소 기록' 판정에는 T5·T6를 하는 동안의 행동(화면에서 주소 기록을 찾았는지, 요청자나 진행자에게 물었는지)만 쓴다.
  - 이 질문은 정답 여부를 알려 주지 않는다. 답을 들은 뒤에는 "고맙습니다"만 한다.
- **A1-05·A1-06 판정(1.3절 가):**
  - A1-05는 T5·T6를 하는 동안의 행동으로만 판정한다(`address_compared`, 잘못 누른 횟수). 두 결정 사이에는 SEQ와 확신만 물으므로, 키트의 질문이 T6 행동을 이끌지 않는다. 앞 건을 먼저 해 본 데서 오는 순서 효과는 남으므로 순서 A·B를 나눠 적는다.
  - A1-06은 T6 뒤 질문의 `button_effect_known`으로 판정한다. 기억으로 답한 것과 이미지를 보고 답한 것을 함께 세고, 기억으로 답한 사람 수는 따로 적는다. T5 건은 T6 건보다 결정한 지 오래되었으므로, 기억으로 답한 사람 수로 PC와 휴대폰을 비교하지 않는다.

### 8.1 설계

- **나누는 방식:** 참가자는 무작위로 두 구조 가운데 하나만 본다. 인원은 같게 맞춘다.
- **대상과 제외:** 대상 조건은 2.3절 S1~S6과 같다. 트리 테스트의 확인 질문도 S1~S6을 물으므로, 3.2절 안내에 그 항목을 모두 적는다. 확인 질문을 바꾸면 안내도 함께 고친다. 대면 시험 참가자는 뺀다.
- **과업:** 연습 과업 1개와 본 과업 10개. 본 과업 순서는 무작위로 섞는다. 위로 돌아가기는 허용하고, '모르겠음'도 고를 수 있게 한다.
- **기록:** 첫 클릭 노드, 최종 노드, 성공(직접 / 되돌아간 뒤 성공 / 실패 / 건너뜀), 시간.

### 8.2 과업 문장과 정답

**과업 문장에 쓰지 않는 낱말.** 두 구조의 트리(8.1절)에 나오는 메뉴 낱말을 모두 막는다.

| 구분 | 낱말 |
| --- | --- |
| 현재(A1) 트리 | 출금, 요청, 작성, 홈, 업무, 결재, 조직, 전체, 승인, 내가, 불가, 주소, 중지, 자주 묻는 질문, 보낼 곳, 주소록, 등록, 상태, 목록, 확인, 대기, 사용, 가능, 거절, 자산, 잔고, 활동 내역, 참고, 우리 회사, 입금, 스테이킹, 현황, 지원, 네트워크, 관리, 구성원, 역할, 정책, 감사, 기록, 내보내기, 정보, 마켓 인사이트 |
| B안 트리에만 있는 것 | 보내기, 올린(내가 올린 요청), 진행 상황, 받기, 결재함, 예정, 처리, 완료, 거래처, 새(새 주소 등록), 보유, 증빙, 묶음, 설정, 권한, 규칙, 보기 |

**어간 기준으로 점검한다.** 낱말 그대로만 막으면 활용형이 한 구조의 메뉴 이름하고만 겹쳐, 두 구조에 서로 다른 유도가 생긴다. 그래서 활용형과 그 낱말을 품은 말까지 막는다.

| 메뉴 낱말 | 함께 막는 형태(예) | 겹치는 구조 |
| --- | --- | --- |
| 보낼 곳, 보내기 | 보내, 보낸, 보낼, 보내면, 보내왔습니다 | 두 구조 |
| 받기 | 받을, 받는, 받으려면 | B안 |
| 내가 올린 요청 | 올려, 올린, 올릴, 올려 두려면 | B안 |
| 보기(승인 규칙 보기) | 보려면, 찾아보려면, 맞춰 봐야, 모아 보려면 | B안 |
| 새 주소 등록 | 새, 새로 | B안 |
| 거래처 | 거래를, 거래하는 | B안 |
| 자주 묻는 질문 | 묻는, 물어 | A1 |
| 우리 회사 입금 주소 | 우리, 우리 쪽, 회사 | 두 구조 |
| 정보 | 지갑 정보, 정보를 | 두 구조 |

- **뜻이 같은 말:** 과업의 목표를 말하는 데 꼭 필요한 뜻(협력사, 송금, 지갑처럼)은 쓴다. 그렇지 않은데 한 구조의 정답 이름하고만 뜻이 바로 겹치는 고유어는 피한다(예: 2번의 '기다리는' ↔ B안 정답 '결재함 > 대기').
- **쓰는 말:** 송금, 지갑, 대금, 결정, 협력사, 고객사, 법인, 문자열은 두 구조의 메뉴 이름에 없으므로 쓴다. 기본 동사(가다, 누르다, 찾다, 알다, 만들다, 바꾸다, 저장하다, 대조하다)도 메뉴 이름에 없다. '회사'는 '우리 회사'와 겹치므로 쓰지 않는다.
- **같은 목록을 대면 카드에도 쓴다.** 그중 현재(A1) 트리 낱말은 대면 시험의 인물 카드와 과업 카드에도 적용한다(4.3절).
- **공개 전 점검:** 두 사람이 따로 과업 문장을 낱말 단위로 끊어 위 두 표와 대조하고, 겹친 낱말과 고친 문장을 기록한다. 이 판 문장은 이 방식으로 한 번 대조했다. 그래도 공개 전에 다시 한다.

## 10. 분석 계획

1. **세션 당일 (15분):**
   - 기록 담당이 `tasks.csv` 행을 마저 채우고, 문제 후보를 `issues.csv`에 적는다.
   - 진행자는 기억나는 장면과 의문점을 적는다.
   - 대본 자체에 문제가 있으면 다음 세션 전에 고치고 기록한다. 화면은 바꾸지 않는다.
2. **결정에 직접 쓰는 열은 두 사람이 따로 코딩한다.**
   - 대상 열: `mid8_source`, `oob_contact`, `network_choice`, `evidence_checked`, `address_compared`, `anomaly_result`, `button_effect_known`
   - 녹화를 보고 각자 코딩한 뒤, 다르면 녹화로 합의한다. 합의 전 값도 남긴다.
   - **녹화가 없는 세션**(S11에서 녹화 없이 참여한 사람, 또는 녹화가 실패한 구간)은 진행자와 기록 담당이 세션 중에 각자 코딩한다. 서로의 값을 보지 않고 적고, 세션 직후 정리 시간(15분)에 두 사람의 메모를 맞대어 합의한다. 합의 전 값을 남기고, `participants.csv`의 `notes`에 `live_coding`을 적는다.
   - 기록 담당은 녹화 없는 세션에서 결정 열의 근거가 되는 장면(읽어 내려간 글자가 어디서 왔는지, 어느 번호로 걸었는지, 문서를 보고 체크했는지)을 그때그때 시각과 함께 적는다. 결정표에서는 `live_coding` 세션의 값을 따로 표시한다.
   - 진행자와 기록 담당 모두 benchmark 가설을 알고 있으므로, 코드 정의(9절)를 첫 세션 전에 고정한다.
3. **문제 목록을 만든다.**
   - 같은 원인끼리 묶는다.
   - 심각도는 두 사람이 따로 매긴 뒤 의논한다.
   - 문제마다 `cause_type`, 관련 A1·A2 항목, KODA 결정 번호를 단다.
4. **과업별 요약표를 만든다.**
   - 항목: 'n명 중 성공 m명', 시간 중앙값과 범위, SEQ 중앙값, 결정 열 집계
   - 대면 시험 결과에는 백분율이나 p값을 쓰지 않는다. 3명 중 3명이 성공해도 95% 신뢰구간(adjusted Wald)은 약 38~100%다. 이 사실을 보고서에 적는다.
5. **SUS를 정리한다.**
   - 참가자별 점수와 역할별 중앙값만 낸다.
   - 흔히 인용되는 평균값(68점, Sauro 2011)과는 견주지 않는다. 8명이고 역할이 섞여 있기 때문이다.
6. **결정표를 채운다.**
   - 1.3절 기준을 그대로 적용한다.
   - 기준으로 가를 수 없으면 '판단 보류'로 두고 이유를 적는다.
   - A1 빌드 결과로는 A2의 필요성만 말한다. A2 빌드 결과로만 A2 유지 여부를 말한다.
7. **트리 테스트를 분석한다.**
   - 제외 규칙을 적용한다.
   - 과업별로 성공(직접·간접), 첫 클릭, 시간을 낸다.
   - 두 구조는 과업별 성공률 차이의 95% 신뢰구간(Newcombe 방식)과 참가자별 전체 성공률 평균 차이로 비교한다. 30명 이상이면 참가자 무작위 효과 로지스틱 회귀를 보조로 쓴다.
   - 오답 노드 표를 만든다. 어떤 이름과 헷갈렸는지 보기 위해서다.
8. **두 시험을 맞대어 본다.** 트리 오답이 몰린 곳과 대면 시험의 첫 클릭 오답이 같은 곳인지 확인한다.
9. **결과물을 만든다.**
   - KODA용 한 장 요약: 결정할 항목, 근거, 한계
   - 심각도순 문제 목록
   - 클립 문항(3.1절 마지막 항목)에 동의한 사람의 30초 이내 클립(이름·목소리를 알 수 없게 처리). KODA에 전하는 것은 3.3절 범위를 넘지 않는다
   - 저장소 반영 목록: `traceability.md`에 실제 사용자 결과 행 추가, benchmark 6절 상태 갱신. 반영은 저장소 소유자가 한다.
